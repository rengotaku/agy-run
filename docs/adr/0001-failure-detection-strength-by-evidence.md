## 背景

agy が処理を完遂できなかったのに agy-run が `exit_code: 0` / `error: null` を返す経路があった。画像生成で `generate_image` が 20 回すべて 429 で失敗し 1 枚も生成できなかった実行が、呼び出し側からは成功と区別できなかった。

原因は失敗の分類が `len(body) == 0` の内側にあったこと。agy が失敗を散文で報告すると本文が埋まり、走査そのものが動かない。実装当時のコメントには「agy が exit 0 で本文ゼロを返す silent success を潰す」と書かれており、本文が残る失敗形は想定に入っていなかった。

この結果 JSON を鵜呑みにしたことで、下流で「agy では画像生成ができない」という誤った断定に至り、従量課金の別経路へ切り替えて実費を発生させる二次被害まで起きた。結果 JSON は呼び出し側の判断の起点なので、ここが曖昧だと下流の判断がまとめて狂う。

## 決定

失敗の検出手段を証拠の決定性で 2 段に分ける。

**ログの文字列マッチ（非決定的）** は `warnings` に載せるだけにして、`exit_code` と `error` を変えない。レート制限のシグネチャ走査がこれにあたる。「429 の対処法を調べて」のような調査タスクは本文にもログにも 429 が並ぶため、exit を動かすと誤検知で呼び出し側を止める。

**構造から決定論的に判定できるもの** には exit code を割り当てる。「成果物を作るツールを呼んだのに成果物が 0 件」は transcript の `tool_calls` と実ファイルの突き合わせで確定できるので、`artifact_missing` / exit 43 とした。

既存の `rate_limited` / exit 42 は本文ゼロのときの契約として維持し、`artifact_missing` で上書きしない。呼び出し側は exit 42 を見て `-m` のフォールバック連鎖と `--wait-quota` を回している。

判定に必要な情報が揃わない場合（transcript 不在、conversation id 未解決、壊れた JSON、ログが読めない）は発火させず従来の結果を返す。判定不能を失敗と誤らせない。

## 検討して捨てた案

**本文が非空でも 429 ヒットで exit 42 を返す。** 調査タスクの誤検知で呼び出し側が止まる。文字列マッチである以上、誤検知を前提に設計する必要がある。

**agy のログからツール呼び出しを拾う。** ログにツール呼び出しは記録されない（実測で 6 本走査してヒット 0）。`internal/runcmd` が RUN_COMMAND の失敗をログから拾っている前例があるため最初にここを疑ったが、成立しなかった。読む先は transcript になる。

**ツールの成否を transcript から判定する。** transcript の step が持つキーは `type` / `status` / `tool_calls` / `content` / `thinking` / `created_at` / `source` / `step_index` の 8 つで、ツールの戻り値が残らない。`status` は step の状態（DONE / RUNNING）であって成否ではない。空転検出はこのため「同一ツールの連続呼び出し回数 + 成果物が増えていないこと」を指紋にした。

## 変えてよい前提

- 成果物を作るツールの一覧（現在は `generate_image` のみ）。セットで持っているので追加できる
- 空転判定の閾値（`AGY_RUN_TOOL_REPEAT_LIMIT`、既定 10）
- 空転を検出したときの扱い。いまは記録のみで実行を止めない。実測でループの分布が見えたら自動打ち切りを検討してよい

## 壊すと危ない前提

- **exit 42 の意味**。`-m` のフォールバック連鎖と `--wait-quota` がこれを見て再試行する。別の失敗で 42 を返すと再試行が誤動作する
- **判定不能を失敗にしないこと**。transcript が読めない環境で実行そのものが落ちるようになると、記録のための機能が本来の実行を壊す
- **継続実行での時刻フィルタ**。`-C` では transcript に過去ターンの呼び出しが残るため、実行開始時刻以降のエントリだけを数える。ここを外すとテキスト応答だけの継続が失敗扱いになる
- **秒精度の切り捨て**。`created_at` は秒精度で `time.Now()` はナノ秒精度。切り捨てないと開始と同じ秒の呼び出しを見落とし、検知そのものが無効になる

## テストデータの代表性について

fixture が実データの形式を再現していないと、ユニットテストが全件緑のまま実データで壊れる。この作業中に 2 回踏んだ。

1 回目は #35 で、fixture に `created_at` が 1 件も無かった。実害としてレビュアーが fixture から実形式を推定し「実形式には `created_at` が無いので検知は動かない」と誤った結論を出した。

2 回目は #36 で、マーカー行の fixture を短く省略していたため、実データではモデル名の後ろに続く説明文を拾って `"comment on this change if the user doesn't ask about it"` を記録していた。ユニットテストは全件緑だった。

transcript を読む実装では、fixture を実データの形式に合わせることを必須にする。あわせて、実データに対して 1 回動かして結果を確認するまで完了としない。
